## HTML-in-Canvas

TODO: explain the problem this solves — the historical tradeoff between DOM (accessible, interactive, searchable) and canvas/WebGL (performant, GPU-accelerated, visually expressive). You always had to pick one.

The new HTML-in-Canvas API lets you render actual DOM elements — forms, inputs, text — directly into a WebGL or WebGPU texture. The browser handles layout, accessibility, find-in-page, and screen readers. You get the GPU.

It's in origin trial (Chrome 148–150). To try it in Chrome Canary, enable `chrome://flags/#canvas-draw-element`.

The core API looks like this:

```html
<canvas layoutsubtree>
  <div id="my-element">
    <input type="text" placeholder="I live inside WebGL now" />
  </div>
</canvas>
```

```javascript
const ctx = canvas.getContext('2d');
canvas.onpaint = () => {
  ctx.drawElementImage(document.getElementById('my-element'), 0, 0);
};
```

## Element-scoped View Transitions

TODO: explain what the original View Transitions API was — document-level transitions that animated the whole page between states. Great for page navigations, but clunky when you only want to animate a small component.

Chrome 147 (stable, no flag needed) adds `Element.startViewTransition()`. Instead of transitioning the whole document, you scope it to a subtree. Multiple transitions can run concurrently without blocking each other or the rest of the page.

Before (document-level):
```javascript
document.startViewTransition(() => {
  reorderList();
});
```

After (element-scoped):
```javascript
const list = document.querySelector('.my-list');
list.startViewTransition(() => {
  reorderList();
});
```

The real win: two separate lists can animate simultaneously, and the rest of the page stays interactive during both.
